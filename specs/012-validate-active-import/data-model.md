# Data Model: Active Import Coordination

## Account (existing)

- `Id`, `OwnerUserId`: existing account identity and authorization boundary.
- `ActiveImportId`: existing nullable review lease; acquire only when null and release
  only when equal to the exact review being finalized.
- Existing unique filtered index on `ActiveImportId` and owner index remain.
- An ended operational header must never hold this lease.

## ImportReview (extend existing entity)

| Field | Constraints and purpose |
|---|---|
| `Id`, `AccountId`, `ActingUserId` | Existing identity/account/creating actor; owner is authorized through the account, not merely by knowing the review ID. |
| `State` | Existing states plus `Processing`; preserve existing string storage and increase the allowed-state check constraint. |
| `CreatedAtUtc`, `ExpiresAtUtc` | Existing preview validity; only Ready may expire through this timestamp. Preview lifetime remains five minutes. |
| `SchemaVersion`, `MappingJson`, `Rows` | Existing staging; required for a usable Ready/Processing review, removed when ending. Mapping/schema are already nullable. |
| `DuplicateConfirmationRequired` | Existing warning state; preserve duplicate detection and explicit reconfirmation behavior. |
| `ConfirmationAttemptId` | New nullable GUID, generated by the server before the retried claim operation; required only in Processing. Guards retries, write ownership and failure/recovery cleanup. |
| `ProcessingStartedAtUtc` | New nullable UTC timestamp, required only in Processing; independent of preview expiry. |
| `EndedByUserId` | New nullable bounded user identifier (same 450-character limit as existing actor identifiers); paired with EndedAtUtc only for externally ended Cancelled headers. |
| `EndedAtUtc` | New nullable UTC timestamp; distinguishes external ending from same-session cancellation or expiry. |

### Relationships and indexes

- Retain the Account foreign key and staged-row cascade relationship.
- Keep operational ending-user identity as a value reference, resolved through the
  already authorized account owner/Identity user; do not introduce a cascade path that
  deletes Audit or unrelated financial records.
- Keep the review primary key and existing `(AccountId, State)` and expiry indexes.
- Add a filtered `(ProcessingStartedAtUtc, Id)` index for Processing cleanup if supported
  by the generated SQL Server migration. Validate index use and predicate compatibility
  in the required query review.
- Status loads active and watched headers by primary key within the authorized account,
  with only required Identity columns; never Include staged rows.

### Valid stored shapes

1. Ready: no processing or ending fields; staged rows/mapping valid.
2. Processing: attempt and processing-start present; ending fields absent; staged
   rows/mapping retained until the guarded financial transaction finishes.
3. Externally ended Cancelled: ending-user/time present, processing fields absent, no
   staged rows/mapping/schema; retained solely to notify sessions watching this review.
4. Other terminal reviews: legacy-compatible metadata-null shapes; existing runtime
   paths delete these temporary reviews. Do not start retaining a general import history.

Add check constraints for paired processing fields, paired ending fields and their
allowed states, while allowing pre-migration legacy terminal rows. Transitions must clear
inapplicable fields atomically. Do not require old rows to be updated during migration.

### State transitions

| From | Trigger | To / persistence outcome |
|---|---|---|
| No lease | Valid new preview and successful lease claim | Ready with staged rows, same atomic create transaction |
| Ready, unexpired, matching lease | Accepted confirmation claim | Processing with new attempt/start, short committed claim |
| Ready, unexpired, matching target/lease | End from competing screen | Cancelled operational header; delete staging, clear mapping, release lease and append Audit in one transaction |
| Ready | Same-screen cancellation | Delete review/staging, release matching lease, append existing cancellation Audit |
| Ready, expired | Create-time expiry or cleanup | Delete review/staging, release matching lease, append expiry Audit |
| Processing | Duplicate warning requires another explicit confirmation | Ready after rejecting that attempt and preserving warnings; clear processing fields; retain matching lease |
| Processing | Successful guarded financial transaction | Insert transactions/save settings/update account; delete review/staging and release lease atomically; append success Audit |
| Processing | Known failed/rolled-back attempt | Delete only matching attempt/staging, release its matching lease, append failure Audit |
| Processing, abandoned for five minutes | Guarded recovery wins before financial transaction, or after its rollback | Delete only matching attempt/staging and release lease; append failure/recovery Audit, never an externally ended notice |
| Externally ended header | Notification read or acknowledgement | No server transition; acknowledge by leaving that preview in the browser |

### Concurrency and validity invariants

- Claim, end, expiry and recovery serialize on the same review before touching its
  account lease. Use a consistent review-then-account order; creation uses the account
  only until it has successfully acquired an empty lease and creates a new review.
- Both Ready-to-Processing claim and Ready-to-Cancelled ending are conditional writes
  checking account ownership, exact ID, unexpired Ready state and matching lease. Zero
  affected rows triggers reclassification, not success.
- A missing review behind a non-null lease is blocked/unknown, never assumed safe to
  release. A non-Ready review is not automatically terminal: Processing always blocks.
- Guard financial writes with the same attempt identifier and a write lock retained
  through the SQL transaction. Recheck account/lease and attempt before any insert.
- Recovery may select stale candidates without tracking, but its final conditional write
  must acquire that same lock and recheck after waiting. Time alone never makes Processing
  available. A recovery winner prevents any delayed worker from writing.
- An ended header's ID cannot be reused, confirmed or mistaken for a newly active review.
- Exceptions/retries with an uncertain commit must verify the persisted attempt and
  account state before cleanup; never rerun inserts when a successful attempt is gone.
- Bulk conditional updates bypass EF tracking. Clear/reload tracked review/account
  entities between committed claim and write/finalization phases and on execution-strategy
  retries so stale Ready/lease values cannot overwrite a winning transition.

## Audit (existing, unchanged schema)

Append an external-end event (for example `ReviewEndedElsewhere`) in the same transaction
as ending, using existing acting user, occurrence time, event code and required
human-readable account description. Follow the same pattern for abandoned-claim recovery.
Do not include review/account IDs in Audit, change old records, or add another audit table.

The retained review fields are the minimum current operational state needed to answer a
specific screen's status; Audit remains the canonical append-only event record.

## Status Projection (not persisted)

See [the contract](./contracts/import-coordination.md) for discriminated response shapes.
Derive availability from the account lease plus active header, and the watched outcome
from that specific review even when the account now has a different active import.
Ready at/after ExpiresAtUtc projects Expired; Processing never does. Missing non-active
reviews project Unavailable, never falsely Ended.

## Migration, Deployment and Recovery

- Add only nullable review columns, expanded state/shape constraints and a processing
  cleanup index. No new table, CSV-data copy, Audit alteration or backfill is required.
- Verify upgrading a populated database leaves Ready reviews, mappings, balances,
  settings, account leases and every Audit record unchanged.
- Deploy during a brief import-route maintenance window after draining in-flight import
  requests. Apply the migration, deploy the coordinated backend, then the frontend;
  do not run old API binaries alongside new Processing rows because old cleanup treats
  non-Ready as terminal.
- The legacy account-only end endpoint will require an exact review target. Old clients
  without it fail explicitly rather than cancelling an arbitrary new review.
- Prefer forward fixes. A binary rollback to the old backend requires blocking import
  routes and draining or safely recovering every Processing claim first. Never drop
  operational ending metadata or mutate Audit as an automatic rollback step.
- Integration tests cover upgrade and the existing Audit immutability guards; an
  independent agent reviews generated migration and actual statement/lock behavior.
